Lecture 10 – Polymorphism

The big idea · read, don't copy

The whole lecture answers one question: when you call ptr->talk() through a Bird* that's actually pointing at a Chicken, whose talk() runs? By default C++ decides at compile time from the pointer's declared type, so you get Bird's version. If you mark the function virtual, C++ waits until the program is running and uses the type of the object actually being pointed at, so you get Chicken's version.

That's what lets one vector<Bird*> hold Chickens, Ducks and Eagles and have each one talk correctly, which is exactly how Project 3's vector<Player*> works. The rest of the lecture follows from that: abstract classes, interfaces, factory functions, and when a derived class counts as a real subtype.

Polymorphism

Polymorphism literally means "many forms". It's the ability for one piece of code to behave differently depending on how it's used.

  • There are 3 kinds: function overloading (ad-hoc), templates (parametric) and subtype polymorphism.
  • When people say polymorphism they almost always mean subtype polymorphism: a variable of the base type (e.g. Bird*) can hold an object of a derived type (e.g. a Chicken).

Use pointers, not values

Because C++ has value semantics, Bird b = c; tries to cram a Chicken's worth of data into the space for a Bird. It compiles, but only the Bird part gets copied over. This is called slicing, and b is now just a plain Bird, so it can never act like a Chicken.

  • The fix is to work with objects indirectly, using pointers or references. A Bird* and a Chicken* take up the same space because they're both just addresses.
Chicken c("Myrtle");
Bird b = c;✗ sliced, b is only a Bird now
Bird *bPtr = &c;✓ bPtr still points at the whole Chicken

Static vs dynamic type

The static type of a pointer or reference is the type it's declared with, and it's known at compile time. The dynamic type is the type of the object it's actually pointing to while the program runs.

Chicken c("Myrtle");
Duck d("Scrooge");
Bird *ptr = &c;← static type Bird*, dynamic type Chicken*
ptr = &d;← static type still Bird*, dynamic type now Duck*
  • The static type never changes, but the dynamic type changes whenever the pointer is pointed at something else.
  • The dynamic type must always be the same as, or derived from, the static type.

Upcast vs downcast

The compiler only lets you convert a pointer (or reference) automatically in one direction. Going up to the base type is an upcast and is safe. Going down to a derived type is a downcast and won't compile.

Chicken c("Myrtle");
Chicken *cPtr = &c;
Bird *bPtr = cPtr;✓ upcast, all Chickens are Birds
Chicken *cPtr2 = bPtr;✗ downcast, not all Birds are Chickens
  • If you really need to downcast, use dynamic_cast. It gives back nullptr if the object isn't actually that type, so always check for null. It only works if the base class has at least one virtual function.
Chicken *cp = dynamic_cast<Chicken*>(bPtr);
if (cp != nullptr) { /* chicken-specific stuff */ }
  • Needing dynamic_cast is usually a sign of bad design: every time a new kind of Bird gets added, you'd need another if. Virtual functions solve this properly.

Virtual functions

Member functions are non-virtual by default. For a non-virtual function, the compiler picks which version to call at compile time, based on the static type. This is called static binding. For a virtual function, the choice waits until the call actually happens at runtime and uses the dynamic type instead. This is called dynamic binding.

class Bird {
public:
virtual void talk() const { cout << "tweet"; }
};
class Duck : public Bird {
public:
void talk() const override { cout << "quack"; }← override
};
Duck d;
Bird *ptr = &d;
ptr->talk();← prints quack. Without virtual it would print tweet
  • You only need to write virtual in the base class. The derived version is automatically virtual too.
  • override tells the compiler to check that this function really matches a virtual function in the base class, including const. Without it, a typo like tak() silently creates a brand new function instead of giving an error.
  • This is what makes a vector<Bird*> useful: looping through it and calling talk() on each one prints bawwk, quack, screech e.t.c.

Abstract classes & interfaces

Sometimes the base class has no sensible version of a function. What does a plain "bird" say? In that case we make it pure virtual with = 0, which means there is no implementation at the base level.

virtual void talk() const = 0;← pure virtual
  • A class with any pure virtual function is an abstract class, and you can't create objects of it, e.g. Bird b; is an error.
  • Derived classes inherit the pure virtual functions and stay abstract until they override all of them.
  • You can still have pointers to an abstract class, and they're really useful, e.g. Animal *ptr = &cow; is fine.
  • An interface is a class where every function is pure virtual, e.g. Shape with area() and perimeter(). Classes like Triangle and Rectangle "implement" the Shape interface.
non-virtual"You can't override this." (Redefining it in a derived class just hides it; there's no runtime choice.)
virtual"Here's a default. Override it if you want."
pure virtual"You must override this to fill in the missing function."

Liskov substitution

Not every derived type is a subtype. A derived type is anything that inherits members. A subtype also has to follow the "is-a" relationship.

  • Liskov Substitution Principle: if S is a subtype of T, any code that works with a T should still work if you swap in an S, with no unwanted effects.
  • So a subtype can require less (a weaker REQUIRES) and promise more (a stronger EFFECTS), but never require more or promise less.
  • e.g. if the base function REQUIRES x > 0, a version that works for any x is fine ✓, but one that needs x > 10 breaks code that passes in 5 ✗.

Misc details

  1. Overriding is when a derived class redefines an inherited virtual function. Overloading is when one function name refers to different functions with different parameter types.
  2. Member name lookup starts in the class of the static type (for a pointer, the type it's declared as), then tries the base class, and stops at the first match.
  3. A factory function creates and returns objects, e.g. Bird_factory("blue", "Myrtle") returns a new BlueBird. It lets the program decide which type to make while it's running (e.g. from user input), without the caller needing to know the class name.

slide 7Given Bird b; Chicken c; Duck d;, which of these are safe?

(a) Bird *bPtr = &b; Chicken *cPtr = bPtr;
(b) Bird *bPtr = &b; bPtr = &d; bPtr = &c;
(c) Bird &bRef = c; Chicken &cRef = bRef;
(d) Bird &bRef = d;
Answer

(a) ✗ (b) ✓ (c) ✗ (d) ✓

(a) and (c) convert a Bird into a Chicken, which is a downcast. (b) and (d) only ever convert into a Bird, which is an upcast.

slide 8What are the static and dynamic types of ptr at (1) and (2)? Say random() returns 0.3.

Chicken c("Myrtle"); Duck d("Scrooge");
Bird *ptr;(1)
if (random() < 0.5) ptr = &c;
else ptr = &d;(2) after the if/else
Answer

Static type: Bird* at both. Dynamic type: undefined at (1), Chicken* at (2).

At (1) ptr isn't pointing at anything yet. 0.3 < 0.5, so it gets pointed at the Chicken.

slide 9talk() is not virtual yet. A vector<Bird*> holds a Chicken, Duck, Eagle and Duck, and allTalk calls birds[i]->talk() on each. What prints?

  1. bawwk, quack, screech, quack
  2. tweet, tweet, tweet, tweet
  3. bawwk, bawwk, bawwk, bawwk
  4. Undefined, the code might crash
Answer

B: tweet, tweet, tweet, tweet.

Without virtual, the static type Bird* decides, so Bird's talk() runs every time. Once talk() is virtual, the answer becomes A.

slide 21What does each call print?

class Fruit { public: int f1() { return 1; } virtual int f2() { return 2; } };
class Citrus : public Fruit { public: int f1() { return 3; } int f2() override { return 4; } };
class Lemon : public Citrus { public: int f1() { return 5; } int f2() override { return 6; } };
Fruit fruit; Citrus citrus; Lemon lemon;
Fruit *fPtr = &lemon; Citrus *cPtr = &citrus;
fruit.f2(); citrus.f1(); fPtr->f1(); fPtr->f2(); cPtr->f2();
cPtr = &lemon; cPtr->f1(); cPtr->f2();
Answer

2 3 1 6 4 3 6

Calls on plain objects just use that object's class. Through a pointer, f1 is non-virtual, so it follows the pointer's type (Fruit → 1, Citrus → 3). f2 is virtual, so it follows the object's type (Lemon → 6, Citrus → 4).

slide 26Animal has a pure virtual talk(). Cow and Bird derive from Animal, and only Cow overrides talk(). Duck derives from Bird and overrides it. Which of Animal a; Bird b; Cow c; Duck d; compile, and what can Animal *ptr point to?

Answer

✗ Animal a, ✗ Bird b, ✓ Cow c, ✓ Duck d. ptr can point to c or d.

Animal and Bird are both abstract, since Bird never overrides talk(). You can't make objects of them, but you can point an Animal* at any concrete animal.

slide 35Base Player::play_card() promises to return a card from the player's hand, following the rules of euchre. DerivedPlayer always returns the ace of clubs. Is it a subtype?

Answer

✗ No.

It promises less: the ace of clubs might not be in the player's hand or might not be a legal play.

slide 36Base PPMReader REQUIRES that pixels are separated by a single space. DerivedPPMReader accepts any kind of whitespace. Is it a subtype?

Answer

✓ Yes.

It requires less. Every input the base accepts, the derived one accepts too.
